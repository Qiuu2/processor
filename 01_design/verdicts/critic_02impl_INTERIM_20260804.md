# §1 已坐实的 BLOCKER(结构性,与版本无关)

## ⛔ BLOCKER-1 · 元检查 `check_gates_fire.sh` 的 `expect_red` **分不清「闸门响了」与「命令根本跑不起来」** —— 与前任判 BLOCKER 的 `expect_fail` 是同一个病

**位置**:`02_impl/test/check_gates_fire.sh:67-71`

```bash
expect_red(){ local tag="$1" desc="$2" cmd="$3" w="$4"
  if ( cd "$w/02_impl" && eval "$cmd" ) >/dev/null 2>&1; then
    echo "  [FAIL] $tag ... ⇒ ⛔ 闸门**没有响**"; fail=$((fail+1))
  else
    echo "  [PASS] $tag ... ⇒ 闸门确实变红"; pass=$((pass+1)); fi }
```

**判据 = 「命令返回非 0」。任何非 0 都算「闸门响了」** —— 包括命令不存在、编译不过、语法错。
`expect_red` 被 **11 道闸门**使用(G1–G10 全部)。

### 我的实证(D6-d:拿掉被测物,这个数应该等于多少?)

在当前版本(`322544de60241cbb`)的拷贝上,**只做一件事:把 G10 要调的被测脚本拿走**
(`mv test/check_mutants_valid.sh` 到别处,⛔ 不动任何别的东西):

```
[PASS] G10  把 HPF_AFTER_DYN 改回前任的错误形态 ⇒ 变异自证应变红 ⇒ 闸门确实变红
```

**⇒ 被测脚本已经不在了,G10 仍报「闸门确实变红」。**
它变红的原因是 `bash test/check_mutants_valid.sh` ⇒ `No such file or directory` ⇒ 退出码 127。

**⇒ 答案应是 FAIL,实测是 PASS。**

### 为什么这是 BLOCKER 而不是 MAJOR

1. **`check_gates_fire.sh` 是 `run_all.sh` 的第 0 环、【前置】环**,而且 `run_all.sh` 自己写着:
   > 「⛔ 元检查失败 ⇒ **下面各环的 PASS 不构成证据**(治理 §5 假绿纪律)」

   **⇒ 它是全部绿色的凭据。凭据本身有假绿口,则下游全部绿色的可信度都要打折。**
2. **它是 D6-l 的教科书复发**:前任对 `check_negcompile.sh` 的 `expect_fail` 判 BLOCKER,
   理由一字不差就是这一条。作者**把那一条修对了**(我实证过,见 §2),
   **然后在为回应该 BLOCKER 而新建的元检查里,把同一个病重新写了一遍。**
   > D6-l 原文:「一个病被立法修过之后,下一次它会以『我们已经修过了』的形式回来」。
3. 它不是假想风险。**G10 引用的脚本在我 14:19 的版本锁里根本不存在** ——
   也就是说,在 14:21 之前的某个时刻,`check_gates_fire.sh` 里就有一条
   指向不存在文件的 `expect_red`,而它会报绿。

### 若不修,下游会怎么错

- 任何一道闸门的被测命令因**无关原因**跑不起来(改了文件名、动了包含路径、临时语法错、
  编译器换版本),元检查照报「闸门确实变红」⇒ **该闸门实际已经不设防,而报表全绿**。
- G1/G4/G7/G8 的命令都是 `gcc ... && ./a.out` 形式 ⇒ **任何编译失败都会被记成「闸门响了」**。
  而 `channel-dsp` 正在持续改这些源文件。
- ⇒ 最坏形态:某次改动同时(a)弄坏了一道闸门、(b)让元检查的探测命令编不过 ⇒
  **两个缺陷互相掩盖,报表 100% 绿。**

### 修法(与前任对 `expect_fail` 开的那条同构,两条都要)

- ① **`expect_red` 增加「红得对不对」的内容判据**:每道闸门声明 `want=<正则>`,
  被测命令的输出必须命中该闸门自己的失败特征串
  (如 G2 须命中魔数扫描的报错行、G6 须命中「变异存活」、G9 须命中 run_all 的环名);
  **⛔ 命中 `No such file`/`command not found`/`fatal error:` 一律判 FAIL。**
- ② **每道 `expect_red` 必须配一条 `expect_green` 前置**(未变异时同一条命令必须绿)。
  现在只有 G7pre / G8pre 两道有 —— **11 道里 9 道没有阴性对照**,
  而 `expect_green` 这个函数**作者已经写好了**,只是没在其余 9 道上用(D6-ao:定义了、零使用)。
- ③ 顺带:`mkwork` 用 `cp -r "$ROOT"` 整树复制,**把 `build/` 的残留一起带进工作副本**。
  我的拷贝上 `G8pre` 因此 FAIL(未变异时就是红的);在原始树上不复现。
  ⇒ 元检查的结果依赖跑批前的构建残留(D6-j)⇒ `mkwork` 应排除 `build*/`。

### 复核方式
我给的实证可原样重跑:任取一道 `expect_red` 闸门,把它 `cmd` 里调的脚本改名,
修完后该闸门必须翻 **FAIL** 而非 PASS;正常树仍全绿。
