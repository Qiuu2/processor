## ⛔ BLOCKER-1 · `expect_red` 分不清「闸门响了」与「命令根本跑不起来」——与前任判 BLOCKER 的 `expect_fail` 是同一个病,且长在为回应它而新建的文件里

**位置**:`test/check_gates_fire.sh:67-71`

```bash
expect_red(){ local tag="$1" desc="$2" cmd="$3" w="$4"
  if ( cd "$w/02_impl" && eval "$cmd" ) >/dev/null 2>&1; then
    echo "  [FAIL] $tag ... ⇒ ⛔ 闸门**没有响**"; fail=$((fail+1))
  else
    echo "  [PASS] $tag ... ⇒ 闸门确实变红"; pass=$((pass+1)); fi }
```
**判据 = 「命令返回非 0」⇒ 任何非 0 都算「闸门响了」。** 在 tag 上:`expect_red` 用了 **11 次**,
`expect_green`(阴性对照,**作者已经写好了这个函数**)只用了 **2 次** ⇒ **11 道里 9 道没有阴性对照**。

**我的实证(D6-d,tag 的拷贝上,只做一件事)**:把 G10 要调的 `test/check_mutants_valid.sh` 拿走 ⇒
```
[PASS] G10  把 HPF_AFTER_DYN 改回前任的错误形态 ⇒ 变异自证应变红 ⇒ 闸门确实变红
```
**被测脚本已经不在了,它仍报「闸门确实变红」** —— 变红的真实原因是退出码 127(`No such file`)。
**⇒ 答案应是 FAIL,实测是 PASS。**

**为什么是 BLOCKER**:
1. `check_gates_fire.sh` 是 `run_all.sh` 的**第 0 环、前置环**,而 `run_all.sh:29-32` 自己写着
   「⛔ 元检查失败 ⇒ **下面各环的 PASS 不构成证据**(治理 §5 假绿纪律)」⇒ **它是全部绿色的凭据。**
2. G1/G4/G7/G8 的 `cmd` 都是 `gcc … && ./a.out` 形式 ⇒ **任何编译失败都会被记成「闸门响了」**,
   而 `channel-dsp` 正在持续改这些源文件。**最坏形态**:某次改动同时弄坏一道闸门、又让探测命令编不过
   ⇒ **两个缺陷互相掩盖,报表 100% 绿。**
3. **它是 D6-l 的教科书复发**:前任对 `expect_fail` 判 BLOCKER 的理由一字不差就是这条;
   作者**把那一条修对了**(我在 tag 上实证确认闭合),**然后在为回应该 BLOCKER 而新建的元检查里,
   把同一个病重新写了一遍。**
4. **⭐ 而正确写法就在同一个仓库、隔壁文件里**:`check_mutants_valid.sh:61-66` 的 `phase_a_flip`
   **明确区分了「探针取不到位置」与「位置没翻转」,两种都判 FAIL**,并写着
   「⇒ 探针本身失效 ⇒ 本条自证无意义,判 FAIL(**⛔ 不得当作通过**)」。
   **⇒ 同一位作者、同一天、同一套逻辑,在一个文件里做对了、在另一个文件里做错了。**

**修法**(采纳 lead 已路由的层级 —— 立规矩而非打补丁):
- ① `expect_red` 加**内容判据**:每道闸门声明 `want=<正则>`,被测命令输出须命中该闸门自己的失败特征;
  **⛔ 命中 `No such file`/`command not found`/`fatal error:` 一律判 FAIL**;
- ② **11 道全部配 `expect_green` 阴性对照**(函数现成,只是没用 —— D6-ao:定义了、零使用);
- ③ 立规:**凡【以退出码判定被测物行为】的函数,必须同时有【内容判据】+【阴性对照】**。
  全库现有 3 个(`expect_fail` ✓ / `run_neg` ✓ / `expect_red` ⛔)。

**复核方式**:任取一道 `expect_red` 闸门,把它 `cmd` 里调的脚本改名 ⇒ 该闸门必须翻 **FAIL**;正常树仍全绿。
